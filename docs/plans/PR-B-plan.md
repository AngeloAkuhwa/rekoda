## 1. OD-40: three timestamps

`provider_paid_at` (payment time verified from Paystack), `provider_settled_at` (nullable, settlement confirmed by Paystack), `units_credited_at` (when Rekoda credited units). Existing: `subscription_charges.paid_at`, `payments.settled_at`, `usagePeriod(input.when)` in `billing.service.ts` (~650-665). Additive nullable columns; `provider_paid_at` and `provider_settled_at` only from verified Paystack evidence (verify response, signed webhook, settlement record); `units_credited_at` is NOT a provider time: it is set from Rekoda's own committed credit (the database time of the transaction that credits the units, in that transaction), and backfilled only from a stored record of that credit, otherwise null; historical rows backfilled only from stored signed events, otherwise null; never overwritten by an older or less authoritative value (conditional update). No change to accounting or unit crediting. Reports and reconciliation label the three times separately. Tests: provider time vs receipt time, null settlement, separate credit time, delayed, duplicate and out-of-order webhooks, missing history, UTC, retry.

## 2. OWN-73 and 3. OWN-76: dead jobs

Hook on the transition to `dead` in both `markFailed` and `reclaimStalled` (`packages/db/src/repos/jobs.ts`), in the same statement or transaction, idempotent per job id.

- `payment.process`: merchant exception reuses the reconciliation exception queue (`settleRepo.recordException`, `/v1/payments/exceptions`, `/app/payments`, dashboard `exceptionsOpen`) with a new reason worded for merchants.
- `billing.process`: a separate billing notice/status on the billing page and dashboard (D4 option 1), never in the merchant's reconciliation.
- Operations queue: reuse `GET /v1/ops/exceptions` by flagging the attributed event (`external_events.error` set, `processed_at` left null, so it stays recoverable). That listing returns event ids, not job ids, so each item must carry the dead job's id explicitly: before prescribing the source, establish the existing event-to-job association (the job payload's `eventId`), store the job id with the exception when the job dies, and return it on the item. A dying job with no `eventId` has no event to flag, so it gets a job-keyed operations item of its own (keyed on the job id, idempotent), never nothing. Tests: both terminal paths, a job with an `eventId` (the item exposes the right job id and the event stays recoverable) and a job without one (a job-keyed item exists, once).
- Recovery: operator-only, `ops:payment`, reason required, re-verifies with Paystack, keyed on the Paystack reference, conditional on the exception still open, audited (operator, time, verification, outcome), no automatic replay, poison bound kept (one fresh bounded attempt; a second death reopens the same exception). Existing unique references and charge state transitions prevent a second settlement or extension.
- Tests: both terminal paths, repeats, idempotent exception and queue item, missing or invalid reference, verification failure, successful and repeated recovery, no duplicate settlement or extension, no unintended transitions, merchant status and operator authorisation, tenant isolation.

## 4. OWN-70: live-key renewal safeguard

Existing (PR #418): `chargeGate` in `apps/api/src/billing/paystack-key.ts` refuses a live-key plan, pack or checkout charge without `REKODA_PAYSTACK_PLATFORM_CONFIRMED`. Gap to close: the renewal path (`renewal-sweep.ts` and any renewal charge initialisation) must apply the same gate: a blocked renewal is recorded, not marked paid, raises an operations exception and an operator alert, and keeps payment and subscription state. Two cases are distinct. (a) An existing payment (a Paystack reference and a verified provider event) resumes after confirmation only through OWN-76's verified recovery path. (b) A renewal blocked BEFORE initiation has no Paystack reference or event, so there is nothing to verify or replay and the recovery path does not apply to it; how, or whether, it resumes is the open owner question OD-44 (may confirmation permit a fresh, gated initiation?), and PR B builds no resume for case (b) until OD-44 is ruled. OD-44 also asks whether and when access expires while a renewal is blocked; until ruled, PR B keeps OWN-70's behaviour (the renewal row and the grace clock run as today) and assumes no other expiry or resume policy. Nothing treats an unverified or never-initiated payment as recoverable. Tests: blocked and confirmed live key, test key unaffected, provider success and failure, duplicate and delayed webhooks, application failure after provider success, operator recovery and repeat, cancelled and expired subscriptions, no duplicate extension. No live charges.

## 5. OD-37: plan-field trigger

`BEFORE UPDATE OF plan, plan_expires_at ON businesses` (fires only when a value changes) refusing unless the change comes through the sanctioned writers. A transaction-local setting is NOT the authority on its own, because any caller with SQL access can set it: the writers are SECURITY DEFINER functions owned by a dedicated role, the trigger accepts a change only when `current_user` is that role (set by the definer function, not by a GUC a caller can set), and the application and worker roles get EXECUTE on the functions but no direct path to the columns. Test: setting any session or transaction setting directly does not authorise a plan update; owner-role bypass for migrations and administrative repair. Sanctioned writers (from the G-62 guard, `packages/db/src/billing/plan-expiry-files.test.ts`): `subscriptions.writeSubscriptionState` (provider cycles: first purchase, renewal, upgrade, scheduled downgrade taking effect; operator `billingRepo.setPlan` corrections) and `subscriptions.expireSubscription` (lapse); the trial row is an INSERT (`identity.createBusinessWithOwner`), which the trigger does not see. Sensitive changes are audited as today (`plan_changed`, `subscription_expired`). Test fixtures that set plans directly (about 25 files) get a helper. Tests: each valid transition, direct write refused, unrelated job refused, owner repair, tenant boundary, migration apply and rollback.

## 6. G-119 / OWN-77: staging tools (Route A)

`apps/api/src/health/staging-tools.controller.ts` (scope `ops:staging`, a new operator scope), runbook `docs/runbooks/staging-test-business-tools.md`. Enabled only when all hold, else the routes refuse and write nothing: `REKODA_STAGING_TOOLS=1` (parsed like `zeroOrOneFlag`; any other value refuses to boot; set only in the staging host `.env`, never in `docker-compose.prod.yml`, and `scripts/check-staging-deploy.mjs` asserts the compose file never sets it); a database marker; Paystack key kind `test` (boot refuses the marker with a live key; `REKODA_PAYSTACK_PLATFORM_CONFIRMED` set also refuses); the business designated as a test business. Date moves (trial end, paid-to, renewal) go through the OD-37 sanctioned function with 90-day bounds, compare-and-revert rollback, append-only audit (operator, business, before, after, reason, time, outcome). Manual acceptance scenarios for the owner (SUB-ACC 17, 18, 19, 22; ACCEPT-01 2, 3, 9, 10) are written into the runbook with preconditions, configuration, steps, expected results, failure conditions, evidence and cleanup.
