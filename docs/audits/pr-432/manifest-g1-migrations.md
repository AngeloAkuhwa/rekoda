## Findings

### G1-1: MINOR. The application can open a charge with refund and credit facts already set (0230)

- **File:** `packages/db/migrations/0230_refund_through_the_operator.sql:218-235` (the INSERT branch of `rekoda_private.subscription_charges_settlement_guard`, the definition live at head).
- **Description:** 0230 adds `credited_units`, `credited_unit`, `credited_period` and `units_revoked_at`, and freezes them on UPDATE for every runtime role (lines 264-272 and 328-335 of the file). The INSERT "pristine pending charge" list was not extended, so `rekoda_app` (which holds table-level INSERT, 0209) can insert a pending pack charge with any of them set. The settlement INSERT branch is not affected, because settlement has no INSERT grant since 0217.
- **Failure scenario:** A holder of the application credential opens a pending pack charge with `credited_units = 1`. The merchant pays it. Settlement calls `usage_credit_pack`, whose usage-writer stamp requires `OLD.credited_units IS NULL` (0230:245), so it raises 42501. Settlement rolls back, the job retries and dies, and the pack is paid but never credited. Alternatively, `units_revoked_at` is pre-set: the pack is credited, and the operator's refund is later refused as "refunded only once" (0230:401). Both are denial or integrity faults within one tenant. Neither is a forged entitlement. They belong to the class `docs/REKODA_LAUNCH_READINESS.md` OD-51 residual (c) records, but these four columns are not named there, and the 0230 header says "the application ... writes no refund or credit fact".
- **Suggested fix:** Add `OR NEW.credited_units IS NOT NULL OR NEW.credited_unit IS NOT NULL OR NEW.credited_period IS NOT NULL OR NEW.units_revoked_at IS NOT NULL` to the INSERT pristine list in a new migration. Add an ATTACK case inserting each column as `rekoda_app` to `pack-refund.integration.test.ts`.
- **Confidence:** high. The guard text was read at head, and the test file covers UPDATE only.

### G1-2: MINOR. The application credential can close a dead-job operator item with no operator and no audit row (0194)

- **File:** `packages/db/migrations/0194_dead_job_exceptions.sql:216-220`. This grant is still live at head: no later migration revokes it or adds a transition trigger.
- **Description:** `rekoda_app` holds UPDATE on `status, recovery_*, closed_at, closed_by, resolution` of `dead_job_exceptions` for any business it pins. No database rule restricts the transitions, checks that `closed_by` is an `operator:<subject>`, or writes an audit row. The operator resolve path (`dead-jobs.ts:438`) runs on this same credential by design.
- **Failure scenario:** A stolen application credential pins a business and sets `status = 'resolved', closed_by = 'operator:anyone'` on the open record of a dead `payment.process` job. The operator queue and the dead-job alert stop showing a customer payment that was never processed. Or it sets `status = 'recovering'` so that `dead_job_is_recovering` changes the reclaim's behaviour. ADR 0035 Am. 2 rule 4 (every operator mutation is audited) is application-enforced only.
- **Suggested fix:** Move resolve and recovery into definer functions that validate the actor and write the audit row, or note this explicitly beside known R11 as an accepted residual. This is the same class as R11 (actor forgery through the dead-letter requeue).
- **Confidence:** medium. The grant is certain; whether it is an accepted residual is not stated in the migration.

### G1-3: MINOR. Some new DDL is not re-runnable (0194, 0195, 0197)

- **Files:** `0194_dead_job_exceptions.sql:66` (`CREATE POLICY` with no drop or guard); `0195_renewal_blocked.sql:24-33` (two `ADD CONSTRAINT` statements with no guard); `0197_staging_test_business_tools.sql:44, 78, 119` (three `CREATE POLICY` statements with no guard).
- **Description:** A manual re-run (the runbooks' manual-rollback and re-apply path) fails with `duplicate_object`. These three files do not claim re-run safety, and the runner applies each file once, so normal deploys are not affected. Separately, many later files say "Re-running is safe", yet re-running an earlier file after a later one restores weaker definitions. 0223 states this, but most files do not.
- **Failure scenario:** An operator follows a manual rollback and re-apply of 0194 or 0197 and the migration aborts mid-window.
- **Suggested fix:** Wrap the statements in `DO $$ … EXCEPTION WHEN duplicate_object` blocks, as 0213 and 0216 do, or record "not re-runnable" in their headers.
- **Confidence:** high.

### Confirmations (no finding)

- **Membership isolation.** At head no runtime role inherits `rekoda_app` except `rekoda_app` itself. The billing operator lost it in 0211 and settlement in 0217. The 0202, 0216 and 0217 DO-blocks and `boot-checks.ts:105-123` (including table-owner membership) refuse the reverse memberships.
- **Default privileges.** Every new table removes the 0001 (app: S/I/U/D) and 0004 (worker: SELECT) default grants before granting its own: dead_job_exceptions, the four staging tables, renewal_block_close_cursor, plan_change_reviews, both billing_pricing_source tables, usage_reservations and dead_job_enrolment_failures.
- **SECURITY DEFINER functions.** Every definer added in the range pins `search_path` to `pg_catalog[, public], pg_temp`. Each is owned by plan_writer, usage_writer or the migrator (which holds BYPASSRLS, enforced in `migrate.ts:101-122`). Plan-writer and usage-writer definers stay under RLS and the tenant pin. Owner-owned definers all check the pin or are ID-only and worker-only.
- **Later migrations weakening earlier guarantees.** Only R01 (0228 against 0217) and the intended 0209 re-grant of INSERT to app (OD-51, settlement re-prices) do this. Each guard's head definition keeps every clause of its predecessors, apart from the deliberate 0230 removal of the app's paid→refunded move.
