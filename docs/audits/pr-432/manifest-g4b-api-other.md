## Findings

### G4b-1: MINOR: the API's `/v1/ops/refund` reads the operator identity before answering 404, contrary to the guard's stated contract

- Location: apps/api/src/health/ops.controller.ts:83 (class `@UseGuards(OperatorGuard)`) and :500 (method `@UseGuards(OperatorPlaneServedHere)`). The contract is stated at apps/api/src/auth/operator-plane-served.guard.ts:6-8. The order test at apps/api/src/auth/operator-plane-served.guard.test.ts:24-32 covers only `setPlan` and `resolvePlanReview`.
- Description: Nest runs class-level guards before method-level guards. On a production API (OPERATOR_DB null), a request to `/v1/ops/refund` that reaches the API is therefore authenticated and scope-checked by OperatorGuard first, and only then gets the 404 from OperatorPlaneServedHere. The plan routes put the served-here guard first. The refund route does not.
- Failure scenario: a caller on the internal edge or db network, or a path variant that misses Caddy's exact-path `@operator_plane` match (e.g. `/v1/ops/refund/` reaching the API), gets 401 or 403 without a token and 404 only with a valid API-audience `ops:payment` token. That reveals the route and lets the API act as a token oracle. No write is possible: the 404 still comes before any database work, and the API has no operator credential. The doc claim "answered 404 BEFORE any identity is read" is false for this route.
- Suggested fix: make the 404 come before the identity check on this route too. One way is to move the refund handler to its own controller with `@UseGuards(OperatorPlaneServedHere, OperatorGuard)`. Another is a global or class-level served-here check for that path. Then extend the guard-order test to `OpsController.prototype.refund`.
- Confidence: high (guard order verified from source).

### G4b-2: MINOR: the settlement process does not verify that its VAULT_KEY is the database's enrolled key

- Location: apps/api/src/settlement-main.ts:249-256 (boot checks) and apps/api/src/settlement/config.ts:124-127 (format check only). Compare apps/api/src/main.ts, which calls `bootChecks.assertKeyUnchanged(db, 'VAULT_KEY', ...)`, and packages/db/src/repos/boot-checks.ts:301.
- Description: the API and worker refuse to boot on a VAULT_KEY whose fingerprint differs from `key_fingerprints`. The settlement process opens the same sealed Paystack events but accepts any well-formed 64-hex key. Migration 0120 gives `rekoda_settlement` no access to `key_fingerprints`, so it could not run the check as written.
- Failure scenario: a deploy or `.env` edit passes a stale or rotated VAULT_KEY to the `settlement` service only (compose interpolates it separately, docker-compose.prod.yml:279). The process boots, `/health` reports `ok` (it checks only `SELECT 1`), and every `billing.process` job throws "sealed Paystack payload would not open" and retries to dead-letter. Merchants who paid stay unsettled (charge `pending`, plan not applied, pack not credited) while every health signal is green. Money is not lost, and dead-job recovery exists, but settlement silently stops.
- Suggested fix: give `rekoda_settlement` SELECT on `key_fingerprints` (or a SECURITY DEFINER read-only fingerprint check) and call a compare-only variant of `assertKeyUnchanged` at settlement boot. Never enrol from this process. Alternatively, have `/health` attempt to open one recent sealed event.
- Confidence: medium-high (code path verified; the grants were checked via grep of 0120 only).

### G4b-3: MINOR: stale or false comments about which process holds which credential

- Locations:
  - apps/api/src/config.ts:133: `settlementDatabaseUrl` "Held by the WORKER alone (OD-51, migration 0209) ... a production API given one refuses to start". Since 0217 / OD-51.2 a production worker also refuses it.
  - apps/api/src/config.ts:141-143: `operatorDatabaseUrl` "Required in an API process ... Without it the route answers 503". It is forbidden in a production API, and the route answers 404 via OperatorPlaneServedHere. The 503 is reachable only if the guards are bypassed.
  - apps/api/src/main.ts:285: "a production worker holds the settlement credential". The config refuses exactly that.
  - apps/api/src/operator-main.ts:7: "serves only the two operator plan operations". It also serves `/v1/ops/refund` (server.ts:252). The same applies to apps/api/src/operator-plane/config.ts:107: "runs plan changes only under it".
  - apps/api/src/auth/auth.controller.ts:155: "null in a worker process". It is null in every production API as well.
- Failure scenario: an engineer or reviewer who relies on these comments misreads the credential separation that OD-51 depends on. For example, they might give the worker SETTLEMENT_DATABASE_URL to "restore" settlement, or expect a 503 when diagnosing an operator route. No runtime defect.
- Suggested fix: rewrite the comments to match OD-51.1/.2 and 0230.
- Confidence: high.
