## Findings

### G4a-1 — MINOR — apps/api/src/health/ops.controller.ts:83 and :499-501

On `POST /v1/ops/refund`, the controller-level `@UseGuards(OperatorGuard)` (line 83) runs before the method-level `@UseGuards(OperatorPlaneServedHere)` (line 500), because Nest runs controller guards before method guards. The guard's own doc (`operator-plane-served.guard.ts`) and the ops.controller comment say a host without the operator credential answers 404 "BEFORE any identity is read". That holds for the plan routes, where auth.controller.ts:386/406 orders them `(OperatorPlaneServedHere, OperatorGuard)` and `operator-plane-served.guard.test.ts` asserts the order. It does not hold for refund, and that unit test checks only `setPlan` and `resolvePlanReview`.

**Failure scenario:** a production API host (OPERATOR_DB null) that is reached directly, bypassing the Caddy `@operator_plane` matcher, answers 401 to an unauthenticated refund request and 404 to a valid ops:payment token. That reveals the route exists and lets the API act as an oracle for token validity, which OD-51.1 says the API must not be. No write is possible, because the handler is never reached with a null operatorDb.

**Fix:** move refund to method-level `@UseGuards(OperatorPlaneServedHere, OperatorGuard)`, for example in a small separate controller or by overriding the guard order. Extend the guard-order unit test to `OpsController.prototype.refund`, and add an API-host test that asserts a 404 with no token when OPERATOR_DATABASE_URL is unset.

**Confidence:** high.

### G4a-2 — MINOR — apps/api/src/health/ops.controller.ts:137-164 vs apps/api/src/health/ops-alerts.ts:66-99

`GET /v1/ops/health` documents its `alerts` as "judged the same way the alert pass judges it (G-26)". It passes `billing: { blockedRenewals }` only. The alert pass (`collectOpsSnapshot`) also passes `blockCloseFailed` and `blockCloseStalled` from `blockCloseCursorStatus`.

**Failure scenario:** the block-close pass is failing or stalled. The webhook sink pages `billing.renewal_block_close_failing` or `..._stalled`, but an operator polling /v1/ops/health sees neither alert and concludes the platform is healthy.

**Fix:** build both from one shared snapshot (call `collectOpsSnapshot(this.workerDb)` in health()), or add `blockCloseCursorStatus` and the same max/stalled derivation. Add a test asserting that the health alerts include the block-close keys.

**Confidence:** high.

### G4a-3 — MINOR (test gap) — apps/api/src/health/ops-object-authorisation.integration.test.ts:29-134; apps/api/src/health/dead-job-enrolment-routes.integration.test.ts:52-56

The HTTP scope matrix does not include `POST /v1/ops/dead-jobs/:jobId/enrolment-requeue` (ops:payment), `GET /v1/ops/dead-jobs/enrolment-failures` (ops:read) or `POST /v1/ops/refund` on the API host. The enrolment suite constructs the controller directly, so OperatorGuard and the declared scopes are never exercised for these routes. `operatorRoutesDeclareScopes` proves only that a scope is declared, not which one.

**Failure scenario:** a future edit weakens enrolment-requeue to `ops:read`, and every test stays green.

**Fix:** add these routes to the vertical matrix (401 with no credential, a session or a forged token; 403 for ops:read and ops:staging on requeue) with snapshot equality.

**Confidence:** high.

### G4a-4 — MINOR — apps/api/src/health/ops.controller.ts:705-720

The generic `resolveException` checks `deadJobsRepo.openJobForEvent` on the worker credential, then resolves the event in a separate statement and transaction (`events.resolveExceptionAsOperator`). The check and the write are not atomic.

**Failure scenario:** a payment job for the event dies and enrols its dead-job record between the check and the resolve. The event is then closed through the generic path while its dead-job record and the merchant's `payment_processing_stopped` exception stay open: the split state the guard exists to prevent (OWN-73/76). The window is narrow, because the death and the enrolment must fall inside one request.

**Fix:** have the resolve SQL refuse when an open `dead_job_exceptions` row references the event, in the same statement or transaction under the event's pin, or lock the event row before the check.

**Confidence:** medium-low; this depends on the event being both flagged and eligible for a new death at the same moment.

- R11: `requeueEnrolment` passes the verified actor, but the application credential can call the function with any actor.
