## Findings

### G3-1: IMPORTANT. A ₦0 upgrade settled late is recorded as a paid charge that was not applied, and the merchant is told things that are not true
- Where: apps/api/src/jobs/apply-no-charge-upgrade.handler.ts:31-54; apps/api/src/billing/billing.service.ts:546-562 (`awaitNoCharge` maps "settled but unapplied" to `processing`); the copy it feeds is in apps/web/src/app/app/billing/page.tsx:236-240 and apps/web/src/lib/payment-record-copy.ts:45-48.
- What happens: before this PR the API applied a zero-priced upgrade in the same transaction that checked `planExpiresAt > now`. Now the API only opens the charge and queues `billing.apply_no_charge` to the settlement process. The handler checks status, kind, amount and superseded, but not whether the cycle is still live. `applySettledCharge` then marks the charge `paid`, with provider reference `no_charge:<ref>`, and sets it aside as `cycle_ended`. A charge that does not re-price to zero is set aside as `price_not_verified`. `awaitNoCharge` returns false for any non-pending charge that has `unappliedAt` set, so the API answers `processing`.
- Failure scenario: a merchant with 40 minutes left in the cycle upgrades. The settlement process is backlogged, restarting or retrying (up to 5 attempts with backoff), and the job runs after plan_expires_at. Three things go wrong:
  1. The API returned `processing`, and the page says "We are switching your plan on now… Refresh this page in a moment to see your new plan". The plan never switches.
  2. The payment record shows "Payment received, not applied: Paystack confirmed this payment… Contact support to have it applied or refunded", but no payment existed.
  3. A ₦0 "paid" charge lands in the operator's paid-but-unapplied queue.
- Suggested fix: in the handler, under the business lock, retire a ₦0 upgrade whose cycle has ended (or whose price no longer verifies) without settling it, so it never becomes `paid`, and audit the outcome. Make `awaitNoCharge` return a distinct state, such as `unavailable: cycle_ended`, when the charge is retired or unapplied. Give no-charge records a `paid_not_applied` wording that never mentions Paystack or a refund. Add a regression test that runs the job after plan_expires_at.
- Confidence: high on the code path; medium on how often it happens (it needs a job delay that crosses the expiry).

### G3-2: MINOR. Stale type and comment in the close pass
- Where: apps/api/src/billing/renewal-sweep.ts:301-302. The signature is `deps: Omit<RenewalSweepDeps, 'settlementDb'>`, and the comment says it "needs no settlement pool". `RenewalSweepDeps` has no `settlementDb` field (it was removed under OD-51.2), so the Omit does nothing and the comment describes an earlier design.
- Failure scenario: none at runtime. A reader may wrongly believe a settlement pool is still part of the sweep's dependencies.
- Suggested fix: type it as `RenewalSweepDeps` and drop the comment.
- Confidence: high.

### G3-3: MINOR. The G-57 month-boundary regression test no longer crosses a month in the database
- Where: apps/api/src/jobs/jobs-chat-roles-3.integration.test.ts:126 onwards. The title is "refunds the original month once when a retry crosses the month boundary". Since 0222 the database chooses the metering row from its own clock. The test now seeds `spentRow = usagePeriod(new Date())`, the real current month, and only fakes the JS clock across midnight.
- Failure scenario: a defect that refunds to the retry's (new) month when the database clock really crosses midnight between reserve and refund would not be caught, yet the title still claims that coverage.
- Suggested fix: retitle it (for example "refunds to the row its reservation recorded"), or add a DB-level test that reserves in period A and refunds after the reservation row's period has changed.
- Confidence: medium.

### G3-4: MINOR. A ₦0 upgrade whose job fails on its last attempt leaves no notice for the merchant
- Where: apps/api/src/jobs/apply-no-charge-upgrade.handler.ts:55-68, and billing.service.ts:143-144/184 (`processingIssue` reads only `billing.process` dead jobs).
- What happens: on the final attempt the handler audits, alerts and returns, leaving the ₦0 charge pending. That is by design: it is not a dead job and nothing was paid.
- Failure scenario: the merchant was told "processing… refresh in a moment". They refresh, the old plan is still shown, and no `processingIssue` explains why. The only recovery is to choose the plan again. The ops alert exists, but nothing on the merchant's page reflects it.
- Suggested fix: surface a pending ₦0 upgrade older than the wait window as a billing notice, or retire the charge on the final failure so the page shows nothing pending, and keep the alert.
- Confidence: medium.

### Checked and found sound
- Pack credit happens exactly once. `applySettledCharge` locks the business row (L721), re-prices, rejects a second link of the same purchase (`purchaseCreditedElsewhere`), credits through `creditPack` (stamped once in the DB), and retires the purchase's sibling charges.
- A replacement charge opened at today's price shares the purchase with the charge it replaced (`replaces`).
- An abandoned plan charge that is paid late is still re-priced at its own pricedAt, and stale-decision rules catch a second application.
- Checkout refusal mirrors settlement (B3 binding and the price check), so no link is handed out for a charge whose payment would be set aside.
- The renewal sweep starts the grace clock even for blocked renewals. That follows ADR 0024 while OD-44 stays open, and is noted here, not raised as a finding.
- The no-charge failure path's audit insert is permitted for `rekoda_settlement` (0217 L155).
- The staging faults cannot run in production: config refuses the flag with a live key or the §47 confirmation.
