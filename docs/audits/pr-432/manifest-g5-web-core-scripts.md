## Findings

### G5-1 — MINOR — `scripts/deploy-staging.sh:93-110` vs `:131`
**Description.** `COMPAT_BREAKING_MIGRATIONS` (line 131) includes `0228_worker_reads_no_payload_across_tenants` and `0230_refund_through_the_operator`, but `carries_plan_boundary` (the gate on the OWN-86 pre-start smoke, line 1180) does not list them. The smoke (lines 199-528) asserts on 0228, 0229 and 0230 objects anyway. The two lists are maintained by hand, and no test ties them together (`deploy-staging-compat.test.mjs` covers 0196, 0200, 0202, 0203 and 0217 only). The step and failure messages still say "0196/0200/0202-0206" (lines 1181, 1183, 1185).
**Failure scenario.** Not reachable on this PR's first deploy: staging runs main (0192), so the release carries 0196 and the smoke runs. It becomes reachable for any later release that brings in only 0228/0230-class migrations, or a new compatibility-breaking migration added to one list and not the other. That release stops the writers, migrates and starts with no database smoke, and a missing guard or grant goes undetected. OWN-86 says it should be smoked.
**Suggested fix.** Gate the smoke on `[ -n "$BREAKING" ]`, or derive the gate from `COMPAT_BREAKING_MIGRATIONS`. Add a compat test that a release whose only new tag is 0230 runs the smoke. Fix the stale labels.
**Confidence.** High (code read). Low current impact.

### G5-2 — MINOR — `scripts/deploy-staging.sh:864-884, 1111-1121`
**Description.** The `.env` line checks skip every line that starts with `#`. `deploy-staging-envfile.test.mjs:80-131` proves that Compose reads `NOTE="x\n#"NAME=value` as a new statement. The script backstops this evasion with Compose-resolved checks for the project name and the settlement `PAYSTACK_SECRET_KEY`, but not for `REKODA_PAYSTACK_PLATFORM_CONFIRMED`, which the api and worker receive through `env_file: .env`.
**Failure scenario.** A hand-edited staging `.env` hides `REKODA_PAYSTACK_PLATFORM_CONFIRMED=1` after a multi-line value, and the deploy passes the OWN-70 refusal. The impact is limited: the key must still resolve to `sk_test_`, the staging tools refuse to boot with the flag set (config.ts:920), and `staging-readonly-check.sh` reports the flag afterwards.
**Suggested fix.** Also classify `REKODA_PAYSTACK_PLATFORM_CONFIRMED` from `dc config api` and `dc config worker` (classify it, never print it), as already done for the key.
**Confidence.** Medium-high: it relies on the Compose parser behaviour the repository's own tests demonstrate.

### G5-3 — MINOR — `scripts/restore-drill.sh:31, 96-97` (and `scripts/backup-scripts.test.mjs` BYPASSRLS test)
**Description.** In the default container mode, the drill creates `rekoda_provenance_owner` and `rekoda_owner` with `BYPASSRLS` itself (ROLES_SQL). It then checks that they have `BYPASSRLS` (NOBYPASS), so that check cannot fail. It means something only in `DRILL_DATABASE_URL` mode with pre-existing roles. The backup test asserts on the text, not on behaviour.
**Failure scenario.** A drill PASS reads as proof that a restore keeps the definer roles able to bypass RLS. A real restore that follows a runbook which creates the role without the attribute fails silently, because the drill never exercised that.
**Suggested fix.** Describe the check as guarding the URL path only. Alternatively, have the drill create roles from the same SQL the runbook prints, so a runbook drift fails the drill.
**Confidence.** High.

### G5-4 — MINOR — `scripts/lib/job-payload-reads.mjs:5-8`
**Description.** The header says the worker's credential can read every tenant's job row, so the database cannot refuse an unpinned payload read. That is stale at head: 0228 revoked the worker's SELECT on `jobs.payload` and `jobs`, and the smoke asserts it (`deploy-staging.sh:244-247`). The tripwire also accepts any statement in which the pinned fragment appears anywhere (for example `... OR true`), but the header already states it is a tripwire, not a guarantee.
**Failure scenario.** Documentation only: a reader underestimates the database-level protection, or over-trusts the tripwire.
**Suggested fix.** Update the header to describe 0228's column revoke and `job_payload()`.
**Confidence.** High.

### G5-5 — known R01 — `scripts/deploy-staging.sh:247-249`
The smoke asserts that `job_payload(uuid)` is not executable by `rekoda_app` and `rekoda_billing_operator`, but has no assertion for `rekoda_settlement`. This is consistent with the known R01 (0228 grants settlement). The R01 fix in progress in the working tree (0231, not at head) should add `NOT has_function_privilege('rekoda_settlement','public.job_payload(uuid)','EXECUTE')` and add the 0231 tag to the ledger count (currently 30).

### G5-6 — MINOR — `scripts/check-deploy.mjs:778-781`
**Description.** The "nothing else routed to the operator" guard collects only `reverse_proxy` lines whose own text contains `operator:`. A `reverse_proxy {` block with `to operator:3002` on a later line, or an upstream spelt another way, is invisible to the count. A second route to the operator would then pass CI.
**Failure scenario.** A future Caddyfile edit widens what the internet can send to the operator process and CI stays green. The operator process still 404s any path outside its own route table (server.ts:117-118), so exposure is bounded.
**Suggested fix.** Also match `\bto\s+operator:` and any `operator:3002` token anywhere in the Caddyfile outside the one handle block.
**Confidence.** Medium.

### G5-7 — MINOR — `scripts/deploy-smoke.sh:171-172, 432-434`
**Description.** The generated `PAYSTACK_KEY` is left out of `secrets.txt` (the baked-image scan) and out of the operator's "holds a secret that is not its own" list. The compose guard already pins the operator's environment list, so this is defence in depth only.
**Failure scenario.** A future compose edit hands the operator `PAYSTACK_SECRET_KEY`, or an image bakes it. `check-deploy.mjs` would catch the first, while the runtime smoke would not.
**Suggested fix.** Add `$PAYSTACK_KEY` to both lists.
**Confidence.** High. Low impact.
